ELASTICSEARCH ARCHITECTURE: SHARDS, REPLICAS AND REQUEST FLOW
Voice-over script (one paragraph per scene). Read at a calm pace, about 130 words per minute.
Timestamps match elasticsearch-explainer.mp4 and the HTML player.

[Scene 1 | 0:00-0:30 | Index and shards]
First, our color code, which stays the same in every scene. Green is a primary shard, blue outline is a replica, rounded boxes are nodes, the crown marks the master, the laptop is the client, orange dots are requests and purple dots are responses. Now meet an index: a collection of documents, like a big table full of rows. Elasticsearch cuts it horizontally into shards. Here we get shards A, B, C and D. Each shard holds whole documents, never half a document. A shard is an independent unit: it can live on any node, and it can even move to another node.

[Scene 2 | 0:30-1:10 | Inside a shard]
So what is a shard made of? Zoom in on shard A. Under the hood, every Elasticsearch shard is a complete Lucene index. And a Lucene index is made of smaller pieces called segments. So the hierarchy is: Elasticsearch index, then shards, then a Lucene index per shard, then segments. One Lucene index, which means one shard, can hold at most 2,147,483,519 documents. When you search, the shard has to scan every one of its segments. Many small segments means more work, so Elasticsearch merges small segments into bigger ones in the background. Fewer segments, faster searches.

[Scene 3 | 1:10-1:46 | Primary and replica]
Now a cluster with two nodes, Node A and Node B. Node A holds the primary shards P0 and P1. Each primary gets a replica, an exact copy, placed on the other node. Because both copies hold the same data, a read can be served by either one, which gives us extra read capacity. Notice the rule: a replica never lives on the same node as its primary, because one crash would destroy both copies. Now Node A fails. Its primaries are gone. But the replicas on Node B are promoted to primary, blue becomes green, and no data is lost. Replicas give high availability and extra read capacity.

[Scene 4 | 1:46-2:22 | How a document finds its shard]
How does Elasticsearch decide which shard stores a document? It uses the document's _id. The formula is: shard equals hash of _id, modulo the number of primary shards. Our document has _id 42. The hash turns it into a number, say 9. With 3 primary shards, 9 modulo 3 is 0, so the document goes to shard 0. Same _id, same formula, same shard every time. That is how the document is found again later. But what if we changed the index to 4 primary shards? Now 9 modulo 4 is 1. Elasticsearch would look in shard 1, but the document is sitting in shard 0. That is why the number of primary shards is fixed when the index is created.

[Scene 5 | 2:22-3:02 | Full example: 3 nodes, 2 primaries, 2 replicas each]
Let's build a real example. Three nodes. Node 1 is the master node; it manages the cluster. Our index has 2 primary shards: P0 lives on Node 3 and P1 lives on Node 1. With 2 replicas per primary, each shard has three copies in total, and they are spread so that no node ever holds two copies of the same shard. Now Node 1 fails. It held primary P1, and it was the master. A replica of shard 1 on Node 2 is promoted to primary, and a new master is elected. Both shards still have a primary, so the cluster keeps working.

[Scene 6 | 3:02-3:47 | Writing one document]
Back to the healthy cluster. The client wants to index a document with _id 42. Step 1: the client can send the request to any node. Here it goes to Node 1, which becomes the coordinating node. Step 2: Node 1 hashes the _id and finds that the document belongs to shard 0. The primary of shard 0 lives on Node 3, so Node 1 forwards the request there. Step 3: Node 3 writes the document to primary P0 first, and then forwards the operation in parallel to both replicas of shard 0, on Node 1 and Node 2. Step 4: both replicas confirm to Node 3, Node 3 reports success to Node 1, and Node 1 reports success to the client. The key point: the client hears "success" only after the primary and all the replicas were updated.

[Scene 7 | 3:47-4:31 | Reading one document]
Now the client wants to read document 42. Step 1: it asks Node 1, the coordinating node. Step 2: Node 1 hashes the _id and gets shard 0. Shard 0 has a copy on all three nodes, and any of them can answer. This time Node 1 picks the copy on Node 2. Step 3: Node 2 returns the document to Node 1, and step 4: Node 1 returns it to the client. Let's send the same request again. This time Node 1 picks a different copy, the primary on Node 3. The load is spread across the copies, round-robin. So remember the contrast: writes must go through the primary, reads can be served by any copy.

[Scene 8 | 4:31-5:16 | Bulk request]
What if the client has many documents to index? Instead of six separate requests, it sends one bulk request. Step 1: the whole bulk travels to Node 1, the coordinating node. Step 2: Node 1 hashes each _id and splits the bulk into one smaller bulk request per shard: documents 1, 3 and 4 for shard 0, documents 2, 5 and 6 for shard 1. Step 3: those per-shard requests go out in parallel to the primaries: P0 on Node 3, and P1, which happens to be on Node 1 itself. Step 4: each primary executes its actions one after another, and replicates each action to its replicas in parallel. Step 5: when all the replicas report success, the results are collected by Node 1. Step 6: Node 1 sends all six results back to the client in a single response. One network round trip for many documents. That is why bulk indexing is so much faster.

[Scene 9 | 5:16-5:46 | Recap]
Here is the whole picture. An index is split into shards. Each shard has a primary and replicas. The copies live on nodes, and the nodes form a cluster. Three things to remember. Writes: coordinating node, then the primary, then the replicas, then the acknowledgement. Reads: any copy, primary or replica, can answer. And more replicas give you faster reads and better availability, but not faster writes, because every write still has to reach every copy.
